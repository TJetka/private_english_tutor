The honest gap

One session a week from a workbook is roughly 40 hours a year of contact. That is enough to build a foundation the online conversation tutoring can then exploit, but it will not on its own get him to functional English. The lever that costs you nothing is spacing: 10 to 15 minutes on three or four other days (vocabulary book, re-listening to the unit audio, redoing one exercise) will roughly triple retention compared with a single weekly block. Vocabulary decays fastest, so that is what the midweek minutes should target.

A workable session shape, about 45 minutes: replay last week's audio and re-test 10 old words, then the new course book unit with audio first and text second, then the matching Practice Book pages, and close with him saying five sentences aloud using the new structure so the tutoring sessions have something to build on.

If it were my call: start with DK Beginner's Course plus Practice Book plus 5 Words a Day, and hold Fun Skills in reserve as the follow-on once he finishes, or as the immediate substitute if he rejects the DK artwork on sight.

Ok, so the key is in fact related to the local / device data - not a static key-id connection? If I paste it in another place it wont sync?

No, the opposite. The key is a static server-side id, and pasting the link on another device does sync. That is exactly the join mechanism, and it's the scenario I tested: device B took the key from the URL, pulled, and got device A's full history.

What I explained badly is that there are two ids, and only one of them is per-device.

Key versus shard
KV namespace
└── d:w8wy89yqfsyrfxfd:        <- the KEY. one per learner. static forever.
    ├── xk9rmq                 <- his phone's shard
    └── p4tzvw                 <- the tablet's shard

The key is a random 16-character string, generated once on the first device. It is not derived from the phone, the browser, or his name. It is just a random bucket name. Once it exists it never changes, and any device that opens the URL with #k= that key reads and writes that same bucket.

The shard id is the per-device part, 6 characters, generated separately on each device. That is what stopped the lost-update race: two devices write to two different keys under the same bucket, and a read merges them. It is invisible and you never handle it.

So: one account, many devices. The key is the account.

The real precondition, and it is a trap

The new device also has to know the worker URL. Right now SYNC_URL_DEFAULT in the file is empty, so a fresh phone opening your link will adopt the key correctly, find no worker to ask, and show an empty profile. It looks exactly like sync failing.

Nothing is lost when that happens. Once you paste the worker URL into that device's parent panel, it merges with the server and his history appears. But it is a confusing thirty seconds, and it is avoidable with a one-line edit.

On GitHub, open index.html, find this near the top of the script:
